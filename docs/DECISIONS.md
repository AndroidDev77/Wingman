### D-012 (2026-11-01): Contract v1.1.0 adopted
PR #15 adds, additively (no existing path, operation, field, enum or `ErrorCode` removed, renamed or narrowed; checked by a structural diff of `contracts/openapi.yaml` against v1.0.0):
- **Device event ingest**, `POST /v1/connections/{connection_id}/events`: one `connector_event.v1` envelope, `Idempotency-Key` = `event_id`, permanent dedup, `mock.*` refused on real connections, and send outcomes accepted only for an instruction leased on that connection.
- **A pull-based device outbox with single-use leases** (ADR 0006), `GET .../outbox` (read-only, no text or destination) and `POST .../outbox/claim`: only the dispatcher creates instructions, an instruction is leased at most once and never renewed, and an expired lease means "outcome unknown": never `sent`, never retried automatically.
- **Memory routes**: `GET /v1/contacts/{contact_id}/memories`, `PUT`/`DELETE /v1/memories/{memory_id}`.

The integrator added one clarification before merging: the claim-time policy re-check cancels exactly what pause/takeover cancel, so a `user_manual` send is not canceled by a pause (v1.0.0 `sendMessage` allows it), and an `autopilot` instruction is canceled once `send` is no longer `VERIFIED` (ADR 0005).

**ADR 0004's `send:<message_id>` key example is superseded by D-006:** connector send keys are per attempt (`send:<message_id>:<attempt>`), which ADR 0006 and the v1.1.0 outbox schemas use.

### D-013 (2026-11-01): WING-010 draft approval reasons are content-based only; WING-011 adds policy and stops on anything but `send_candidate`
PR #20 (WING-010) computes `Draft.approval_reasons` in code from the draft's content only: `date_or_commitment`, `sensitive_content` (escalation or a cited sensitive fact), `low_confidence` (confidence under 0.6, or too long for the brevity setting) and `first_message`. The model's output schema has no approval, send, recipient or policy field. It never sets `assisted_mode`, `outside_active_hours`, `capability_unverified`, `send_limit_reached` or `user_rule`. Therefore:
- **WING-011 must add the policy reasons** on top of `draft.approval_reasons` from effective settings, connection capability and state. It must not treat an empty `approval_reasons` as permission to send.
- **WING-011 must treat any `decision != send_candidate` as a stop.** `no_send` and `ask_user` never reach the dispatcher, whatever the mode.
- Drafts are not persisted (no `drafts` table, I-007). `Draft.id` exists only in the response, the idempotency record and the `draft_generated` audit details.

The integrator added one guardrail before merging. Escalation is detected in code from the draft text as well as from the model's own flag, and at least one cited contact message must itself show matching interest. Otherwise the result is `no_send` (`unsupported_escalation`).

### D-014 (2026-11-01): Pause stops automated sends only; takeover cancels everything automated
Owner-side decision, made by the integrator on the owner's behalf (D-011). Contract v1.1.0 says pause "stops every automated send" and also that "the agent may still queue drafts for approval"; this resolves the ambiguity reported in PR #24.
- **Pause** (global or per contact) stops AUTOMATED sends only: `autopilot` sends, including any already queued, which are canceled at pause time, at dispatch and at device claim. While paused, a new draft goes to the approval queue instead of being sent.
- **Not affected by pause:** a send the user explicitly approved (`approved_draft`, including one approved during the pause) and the user's own `sendMessage` (`user_manual`). Pause does not cancel pending approvals.
- **Takeover** (per contact) cancels everything automated for that contact immediately: pending approvals, approved-but-unsent drafts (`approved_draft` messages still `queued`) and their unclaimed device instructions, and queued `autopilot` sends. The agent creates no drafts or approvals for that contact until resume. The user's own `sendMessage` still goes.
- A message a device has already leased (`sending`) cannot be recalled; its real outcome is recorded (ADR 0006).

PR #24's code already matched this (`PAUSE_CANCELS = (autopilot,)`, `AUTOMATED_ORIGINS = (autopilot, approved_draft)`, `recheck_send`). The integrator added HTTP-level tests for it (`backend/tests/automation/test_d014_pause_semantics.py`).

### D-016 (2026-11-01): Contract v1.2.0 adopted: pairing, capability trust, `paused`, `lease_expired`
PR #28 (ADR 0007) resolves I-017. It is additive: the integrator diffed `contracts/openapi.yaml` against v1.1.0 key by key, and nothing was removed, renamed or narrowed. The only changed scalars are `info.version`, `info.description` (changelog) and two enum descriptions. Added: three paths/operations, three schemas, three optional `Connection` fields, and enum values. No new `ErrorCode`.
- **Pairing.** `createConnection` (`POST /v1/connections`): `201` new, `200` when that install is already paired for the platform. `getConnection` and `listConnections` are implemented. `sms` and `android_notification` need a `device_install_id` and a capability document. `mock` is refused in `prod` (`422` at `/platform`) and takes the simulator's own document elsewhere.
- **A client's capability claim is never `VERIFIED`.** A client-claimed `VERIFIED` is stored as `UNVERIFIED`, both at pairing and in later `connection.capabilities_changed` events. A client may lower a capability, or keep a `VERIFIED` the server already holds for the same `connector_version`, but never raise one. So a newly paired SMS connection is never autopilot-eligible.
- **Verification is operator-only, with evidence.** Only `ConnectionService.record_verification` sets `VERIFIED`, through the operator CLI `python -m app.services.connections verify ... --evidence REF`. It has no HTTP route and needs a non-empty reference to a reproduced device run (I-019).
- **Unpair** (`POST /v1/connections/{id}/unpair`) is atomic and effective before the response. The connection becomes `disconnected` with every capability `UNSUPPORTED`. Its unclaimed instructions, its `queued` outbound messages (any origin) and its conversations' pending approvals are canceled with reason `connection_unavailable`, each audited, plus one `connection_unpaired` summary. A leased (`sending`) message cannot be recalled and its late outcome is still accepted. Any other event on an unpaired connection is `422`. No `DELETE`, so history is kept.
- **`ApprovalReason.paused`.** An approval created while automation is paused (global or contact) carries `paused`, alongside any other reasons. `details.checks.paused` stays.
- **`AgentActionType.lease_expired`.** Lease expiry is audited with actor `system`, reason `outcome_unknown`, and details holding IDs and codes only (`instruction_id`, `connection_id`, `attempt`, `outcome: unknown`, `retried: false`). It is never `send_failed`; the message stays `sending` and is never retried automatically.
- Schema: `0001` amended (D-010) with `device_install_id`, `paired_at`, `unpaired_at`, a partial unique index and a CHECK; existing `tests/db` assertions are unchanged.

Integrator work before merging: the Android enums gained `PAUSED`, `LEASE_EXPIRED`, `CONNECTION_PAIRED` and `CONNECTION_UNPAIRED` (`ContractExamplesTest` count 20 to 23). The WING-015 label tables now read `paused` as "Automation is paused", and `lease_expired` as "Phone didn't confirm; outcome unknown" (never sent, never failed). Follow-ups: I-018, I-019, I-020.

### D-017 (2026-11-01): A claim from anything but the paired install is `422` at `/device_install_id` (I-018)
PR #32 enforces the `device_install_id` binding recorded at pairing (ADR 0007) in `claimOutboxInstructions`. A claim from another install, on an unpaired connection, or on a device-side connection that was never paired is `422 validation_error` with pointer `/device_install_id`. The check runs under the user lock, before `dispatch_due`, the claim-time policy re-check, leasing and lease recovery, so a rejected install takes, cancels and recovers nothing. The paired install still recovers its own unexpired leases. A backend-side connection without a binding (`mock`) still answers `200` with an empty list, and another user's connection is still `404`.

**Why `422`:** the contract lists no `403` for this operation, and `422` ("Body or parameters failed validation, or capability/policy rejects the action") is the listed status that fits. `404` would tell the owner that their own connection does not exist. A clarifying note (the rejection rule and the pointer) is scheduled for the **next additive contract change**, together with an update to ADR 0007's "Not covered" bullet. **Done in contract v1.3.0** (D-022): `claimOutboxInstructions` documents the rule and ADR 0008 §9 closes ADR 0007's "Not covered" note.

The Android side handles it (PR #30, integrator commits): `SmsOutboxPoller` treats this `422` as a definitive rejection (drops the claim key, backs off exponentially, never sends, never throws; JVM-tested), and `MockWingmanApi` enforces the same binding.

### D-020 (2026-11-01): `FOR NO KEY UPDATE` is the default exclusive row lock (I-028)
PR #38. Every exclusive row lock taken to serialize decisions or to change non-key columns (user, contact, connection, approval, message, outbox instruction, including the `SKIP LOCKED` claim) is `FOR NO KEY UPDATE` (`with_for_update(key_share=True)`), the lock Postgres's own non-key `UPDATE` takes. It does not conflict with the `FOR KEY SHARE` that foreign-key checks take on parent rows when user-owned rows are inserted, so an ingest's FK checks can no longer close a cycle with a pipeline that holds a conversation update and then locks the user (the I-028 deadlock). It still conflicts with itself and with `FOR SHARE`, so policy decisions, pause/resume/takeover, approve/reject, unpair, claims (`SKIP LOCKED` kept), the dispatcher's `FOR SHARE` re-check and lease handling serialize as before.
- **Use `FOR UPDATE` only where a key change or a delete must be blocked**, with a comment at the call site saying why. Reviewed for PR #38: no locked path changes a primary key or a column of a non-partial unique constraint, except `mark_sent` setting `messages.external_message_id`; that `UPDATE` upgrades its own row lock to `FOR UPDATE` itself, after the message is already held exclusively, which is no weaker than before. Status columns in partial unique indexes (`unpaired_at`, approval `status`, outbox `state`) are not keys. Nothing hard-deletes these rows: account deletion sets `deleted_at` (a non-key update) and the operator's `DELETE FROM users` (I-029) or a future purge deletes with cascade, which takes `FOR UPDATE` itself and conflicts with every lock above, so no path keeps `FOR UPDATE`.
- No retry on `40P01`/`40001` was added; a deadlock still fails a request.
- Verified by the integrator: with `main`'s old locks and the new `tests/automation/test_ingest_deadlock.py`, the forced CI interleaving deadlocked 3/3 and the 24-upload stress test failed 2/3; with the fix, 6/6 runs passed. Backend 956 passed, contracts, migrations and the E2E suite passed locally; all 7 CI jobs green on head `d0ff996`.

### D-022 (2026-11-01): Contract v1.3.0 adopted: platforms, transports, experimental consent, notices, assisted delivery, profiles, mark-read

- **Experimental consent (D-021).** `unofficial_api` means `experimental: true` and needs `experimental_consent` (platform, text version, accepted time, `ban_risk_acknowledged: true`); without it `422 experimental_consent_required`, enforced server-side and audited. `revokeExperimentalConsent` runs the unpair transaction (instructions, queued sends, approvals and assisted deliveries canceled; consent `revoked_at`; auto-swipe off). Every request body rejects unknown fields.
- **Identity.** Only a `chat_message` with `identity: linked`, not `truncated` and not `content_hidden`, becomes a `Message` and reaches the pipeline; everything else is an `InboundNotice` with no contact, conversation, draft or send. `source` must equal the connection's transport. SMS with `send: UNSUPPORTED` still blocks.
- **Swipe execute gate.** `requestProfileActionExecution` only moves `not_executable` to `queued` after every gate check (not `skip`, paired and connected, `swipe` VERIFIED, auto-swipe on, not experimental-unverified, not paused, same platform, not stale, no other live action); no code sets `executed`. Device-side outcomes are WING-031's.
- **Mark-read** (`markConversationRead`) is idempotent and user-scoped; every new route answers another user's resource with `404`.
- Android: enum parity (`ErrorCode` 18, `AgentActionType` 35, `DeliveryState` 9, `MessageOrigin` 5, six new enums), labels never upgrade a state. `0001` amended (D-010; 24 tables).

### D-025 (2026-11-02): Contract v1.3.1: ranked review queue and `include_excluded`

### D-026 (2026-11-02): Experimental build mechanics for the unofficial-API Hinge connector
